## Four things you may change, two colours set

A campaign may change four things about how semiplane looks — and this one sets two of
them. Not a fifth, and not the accessibility tokens; the split is enforced by the shape
of the code that produces the stylesheet, not by a filter someone maintains.

## It is a manifest, not a stylesheet

A campaign's brand is **`theme.yaml` at its content root** — an ordinary file in the
vault, which is exactly the point, because a vault arrives by sync client as often as
by hand and a file a Game Master can see and edit is one they can fix. This campaign
has one:

```yaml
# theme.yaml — this campaign's whole brand.
tokens:
  --brand-accent: "#55796b"
  --brand-accent-ink: "#ffffff"
```

Two declarations, and both are load-bearing: the accent alone is refused, because a
brand pair is both-or-neither. The server reads it, validates it, and **generates**
`/c/{slug}/theme.css` on every request; the shell links that address in a campaign
page. A campaign cannot ship a stylesheet, because a stylesheet is a document that can
set `--focus-ring` and there is no gate anywhere that could see it across every
campaign.

## Four names, and the rest are not yours

A campaign may set `--brand-accent`, `--brand-accent-ink` and `--brand-header-image`,
plus two font slots (`--font-prose` and `--font-ui`) through a `fonts:` section that
names a file in the content root. Everything else belongs to the product: the text and
border colours, the focus ring, the callout surfaces, the type and space scales, the
minimum target size, the durations and the radii, and `--font-mono`, which stays fixed
because code and dice expressions must remain monospaced.

**Why it is a closed list and not a protected one.** The generator iterates the
vocabulary it is willing to emit. There is no code path by which `--focus-ring` can
reach the output — not a check that catches it, a loop that cannot name it. A
denylist would be a list of names somebody thought of, and the token added to
`tokens.css` next quarter would be settable until somebody remembered.

## The floors, and why there are two of them

`--brand-accent` is measured against **two** other colours, and `--brand-accent-ink`
sits on top of it:

- **4.5:1** against `--brand-accent-ink`. The ink is text on the accent, so this is
  the text floor.
- **3:1** against `--bg`, **in both the light and the dark page.** §4.12.3 names
  `--bg` without naming a theme, and that omission is the interesting part: a mid-tone
  that clears 3:1 on the light page fails on the dark one. So the accent is checked
  twice and refused once.

Greyhaven's pair, measured against each floor. The accent is `#55796b`:

| Measured against | That colour is | Ratio | Floor |
| --- | --- | --- | --- |
| `--brand-accent-ink` | `#ffffff` | 4.85 | 4.5 |
| `--bg`, light page | `#f7f6f3` | 4.48 | 3 |
| `--bg`, dark page | `#14181d` | 3.68 | 3 |

Only `#rgb` and `#rrggbb` are accepted, and the seven-character grammar is
load-bearing: a floor cannot be evaluated against `var(--x)` or the word `navy`, so a
value the validator cannot compute is a refusal with a reason rather than a floor it
declines to check.

**The pair is both-or-neither.** An accent with no ink is refused, and an ink with no
accent is refused, because there is no such thing as half a pair and honouring one
half would put text on a colour nobody checked.

The window is narrow, and that is arithmetic rather than caution. A colour has to be
dark enough for white ink to clear 4.5:1 **and** light enough to clear 3:1 against the
dark page, and the two constraints squeeze from both sides. There is no accent that
comfortably clears everything; there are only accents that clear all three with room
to spare, like this one.

## When it goes wrong

Two failure directions, and they are deliberately different answers:

- **Refused content** — a floor missed, a protected name, a malformed key, a path
  outside the content root, an over-long token name. The campaign keeps the **last
  sheet that passed** and one error-level line is logged. A rejected theme degrades to
  the default; it never ships an unreadable UI, and it never takes the campaign's whole
  appearance hostage over one colour a Game Master typed.
- **An unreadable file** — not a rejection of anything, a fault in the running process
  looking at a file that may be perfectly good. That answers **500**. Answering "no
  theme" would be a lie served to every reader of the campaign.

A file a Game Master deletes is a *withdrawal*, and it clears the remembered sheet —
otherwise deleting the manifest would leave the brand in place for ever.

## The sheet is the same for everyone

The generated bytes are byte-identical for every reader and every light/dark
preference, with a strong validator salted on the campaign id — the same reason the
page's own validator is salted on whether secrets are included. One campaign's brand
cannot be served from another's request, and the sheet carries no reader-specific
value for the same reason the page's render is permission-neutral.

The sheet is per request and never written to disk: a file on disk would be a second
answer to what the manifest says, and keeping the two in step would need a writer, a
watcher hook and a cleanup path.

## And what a raw `.css` file does

A `.css` inside a content root is an ordinary vault file. The asset route will serve
it, because a page may embed one. **No response the theme route produces ever names
it**, and the brand is not it — if you want a colour, the manifest is where it goes.
