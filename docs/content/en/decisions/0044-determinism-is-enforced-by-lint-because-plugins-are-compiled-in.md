## Context

There is no sandbox. S-10.1 makes a plugin a compiled-in Go module registered explicitly at the composition root, so a gameplay plugin runs in-process with the server's full authority: it can open a file, read a database handle it was handed, and call anything in the standard library. §10.3 states the consequence in one sentence — rule code is forbidden from calling `time.Now`, ranging over a map, or calling `crypto/rand` directly — and gives the reason: `campaign_state` supports optimistic client apply, resume-by-version and replay, all of which break if resolution is not a pure function of `(state, intent, seed)`. It then says "the enforcement is a lint rule plus tests", and that is the whole of what §10.3 says about enforcement.

Two mechanisms, then, and the obvious way to build them is the one that produces the bug this record exists to prevent. Write the forbidden identifiers in `.golangci.yml` because a linter configuration is YAML and there is nowhere else to put them. Write the same identifiers in a Go test because a linter does not run on every machine that runs `go test`. Two lists, one question, and the second list is edited by whoever last touched the rule — which is not the person who thinks about how a resolution can go wrong.

The failure is silent in the expensive direction. A lint pattern that was deleted still leaves the test green; a test case that was deleted still leaves the lint green. Nothing reports a rule that has stopped being enforced, because an unenforced rule produces no output, and the gate that would have noticed is the one that stopped.

Two further facts arrived with the code phase 8 already has, and both are reasons the obvious design does not work here.

**`rules.Context.Rand` legitimately uses `math/rand/v2`.** [0041]({{ "decisions/0041-the-rules-contract-returns-mutations-and-carries-its-own-rng/" | relURL }}) settled that randomness arrives as `Rand(label)`, a fresh `*rand.Rand` derived from the campaign's recorded seed through SHA-256, and that the `gosec` G404 finding on that one call is suppressed inline with that reason. A determinism rule therefore has to distinguish `rand.New(rand.NewPCG(seed, seed))` — the one correct implementation of randomness in this codebase — from `rand.Intn(6)`, which reads a process-global source. Both spell `rand.`. The distinction is a list of selectors, and a rule that gets it wrong is a rule nobody disables: `AGENTS.md`'s own words about a gate nobody runs, applied to a rule that fires on correct code.

**Map iteration is not an identifier.** `for k, v := range m` contains no name the linter can be told about. It is also the failure S-14.6 exists to catch, and the one no amount of careful code review catches reliably, because ranging a map looks exactly like ranging a slice.

## Decision

There is one table, in `internal/domain/rules/determinism`, and both mechanisms read it.

**`ForbiddenRules` is the whole of S-10.4 as this project enforces it.** Nine entries, each `(kind, package, selectors, reason)`, where `kind` is `import`, `call` or `range`. The reasons are written for whoever wrote the offending line, because the useful half of a refusal is what to reach for instead — `range/map` names `slices.Sorted(maps.Keys(m))` as the sanctioned form, and `call/math-rand-v2` names `rand.New(rand.NewPCG(...))` as the one thing the list does not forbid.

**`LintPatterns()` computes the linter's configuration from the table.** Every `KindCall` entry contributes its selectors to the pattern for that package's *name*, because a name is what a selector expression spells: `crypto/rand`, `math/rand` and `math/rand/v2` are three import paths and one package name, `rand`. Selectors are sorted and de-duplicated within a group, so the result is deterministic and readable, and the same table always yields the same patterns in the same order. `.golangci.yml` is not free to hold a hand-written list, because `TestTheLintConfigurationIsTheTableTheAuditWalks` requires it to be exactly what `LintPatterns()` returns — and separately requires that *every* `KindCall` selector is matched by a configured pattern, compiled and run, which is the assertion that proves coverage rather than restating the derivation.

**`ScopePattern()` computes the linter's path scope from `RuleDirs()`,** for the same reason and because the failure is worse: an audit watching a directory the linter does not is a green build with a real nondeterminism in it. The scope names `internal/domain/rules` and `internal/domain/systems`, and the second directory does not exist yet. Naming it anyway is the `A11Y_ROUTE_PKGS` argument: a scope that has to be amended to cover a new package is a scope that will be amended after the violation rather than before it. `Audit` skips a directory that is absent, fails when *no* directory contributed a file, and treats a stat error other than "not there" as an error — because a permission problem reading the rules directory is the shape of a gate that quietly stops auditing.

**`Audit` walks the table over parsed and type-checked rule code.** It parses each `.go` file that is not a `_test.go`, groups the files by their package clause, and type-checks each group with `go/importer`'s source importer — a second resolution against real types rather than a syntactic guess, because the interesting question is whether a range expression's *type* is a map, and only a type checker answers that. A file that does not parse and a package that does not type-check are both **errors**, not findings: an audit that could not read its input and reported nothing is exactly the "audit that cannot fail" this repository has been bitten by twice. Test files are excluded because a test resolves nothing, and because this package's own fixtures are files containing `time.Now`.

**The audit is a strict superset of the linter, and the difference is written down.** It refuses an import, a *reference* to a forbidden selector taken as a value rather than called (`now := time.Now` is the same hole one step earlier), a range over a map, and a range over an iterator from `maps.Keys`, `maps.Values` or `maps.All`. `LintBlindSpots()` names the two rules no selector pattern can express — `range/map` and `range/map-iterator` — and `TestTheLintBlindSpotsAreExactlyTheRangeRules` asserts that list is *exactly* the `KindRange` entries and that no configured pattern mentions `maps` at all. What the linter can reach that the audit cannot: nothing.

**The `maps.Keys` pattern was written, and removed.** It was in `.golangci.yml` as `^maps\.(All|Keys|Values)$`, on the reasoning that ranging an iterator is ranging a map. It fired on `slices.Sorted(maps.Keys(m))` — the sanctioned spelling — exactly as loudly as on `for k := range maps.Keys(m)`, because `forbidigo` sees the call and not what the call is an argument to. That is the same failure `Context.Rand`'s G404 suppression exists to avoid, in the linter's own configuration: a determinism rule that fires on the one correct way to write the thing it forbids gets disabled wholesale by the next contributor, and a disabled rule catches nothing. `Audit` keeps the rule, because it reads the range clause rather than the call and can therefore tell the two apart. The measured asymmetry is recorded rather than asserted: injecting a map range into `internal/domain/rules/context.go` leaves `golangci-lint run` at exit 0 and fails `go test`.

**`internal/domain/rules/determinism` also owns the house-rule scope check.** S-10.5 refuses a module that reorders resolution or introduces nondeterminism, and that refusal has no other enforcement — the lint rule and the audit catch code reaching for a clock, and neither can see a compiled-in module's claim about what it may do. A `Scope` is a list of `Capability` values; `Scope.Admissible()` refuses `CapReorder` and `CapUnseededRandomness` **by name**, refuses an unrecognised capability under `ErrUnknownCapability`, and treats nil and empty as admissible. Refusing an unknown capability is the direction that matters: a capability nobody has classified must not be treated as harmless, because the next build to add one may classify it as a refusal and this build would already have enabled the module. `Admissible` is a pure function over a compiled-in value — no configuration, no database, no registry — so `internal/domain/rules/houserules` can call it at registration without either package importing the other.

**Migration 0010 adds `campaign_rule_modules`,** with two departures from architecture §10.7's sketch. `campaign_id` is `INTEGER`, not `TEXT`: migration 0005 creates `campaigns` with `INTEGER PRIMARY KEY AUTOINCREMENT`, and every other campaign-scoped table in this schema spells the column `INTEGER`. A `TEXT` column referencing an `INTEGER` primary key would store the id as text, and SQLite compares text to integer by class, so a `WHERE campaign_id = ?` issued with an `int64` would match nothing — silently, at campaign load, as an effective ruleset with no modules in it. `TestTheRuleModuleSchemaIsTheOneTheDomainAssumes` reads the declared types out of `pragma_table_info` for exactly that reason. And `ON DELETE CASCADE` is added, which the sketch omits, matching every other campaign-scoped table here. §10.7's other two statements — `campaigns.system_id` and `campaigns.ruleset_version` — were already delivered in migration 0005, which records at length why they are `CREATE`d rather than the `ALTER`s the record sketches.

**`RuleModulesForCampaign` orders by `(position, module_id)`, and the second key is the point.** Two modules may legitimately share a `position`: nothing in the schema declares positions unique, and a GM editing a list has no reason to notice two rows at zero. Over an order that is not total, §10.5's "conflicts resolve first-match-wins" has no referent — the winner becomes whichever row the storage engine returned first, which is the last-write-wins behaviour the sentence forbids, arriving by a different route. `module_id` is unique within a campaign by the primary key, so it cannot tie. `determinism.Order` states the same order in Go, for a caller assembling a set in memory, and the two are held together twice: behaviourally, by `TestRuleModulesForCampaignMatchesTheOrderTheDomainStates`, and structurally, by `TestTheRuleModuleOrderByIsTotal`, which reads the keys out of the compiled statement and sorts a fixture by *those keys*.

**The unit of a write is the whole set.** `ReplaceRuleModules` deletes and re-inserts in one transaction, because applying a half-written module set is not a state this project can describe: a campaign either has the effective ruleset its modules describe or the previous one. Every row is validated before the transaction opens — `rules.ParseID` for the identifier rather than a second implementation of it, a duplicate check that reports the caller's slice rather than the driver's message, and a JSON-**object** check on `config` whose shape is what the column's `DEFAULT '{}'` asserts. Which *keys* a module understands is deliberately not checked: that vocabulary is `houserules`' to write.

## Consequences

The table is the only place a determinism rule is written down. Adding a selector means editing `forbiddenRules` and nothing else; `.golangci.yml` fails the build if it does not say what the table derives, and `TestTheLintBlindSpotsAreExactlyTheRangeRules` fails if a `range` rule is quietly promoted or demoted.

The audit costs real time, and the cost is stated because a gate nobody can afford to run is a gate nobody runs. `go test -race` for this package takes about 8 seconds, of which roughly half is type-checking `determinism`'s own dependency graph (`go/types`, `go/importer`, `go/parser`) from source, because the audit polices itself and this package is inside the audited tree. The obvious implementation — a fresh importer per audit — measured **41 seconds** instead, because the source importer caches a package's dependencies only within one importer and four fixtures that mention a clock each re-resolved `time`'s whole transitive closure. So there is one resolver for the process, guarded by a mutex, and the audits serialise; the second audit of a package that imports `time` is then a lookup rather than a rebuild. That is the only concurrency this package has, and it is a mutex around a cache rather than a parallel audit.

`forbidigo` replaces its default `forbid` list (`fmt.Print*` and the bare `print`/`println`) as a side effect of being configured here. Nothing in this repository calls them, and the configuration test confirms the default is gone rather than assuming it.

Two layers that are not the same strength will drift if the gap is not written down, so it is written down in three places: `LintBlindSpots()`, the `.golangci.yml` comment above the two patterns, and `TestTheLintBlindSpotsAreExactlyTheRangeRules`.

Two mutations did not fail any test, and both are recorded because "a test that cannot fail is not a test" cuts both ways — a mutation that changes behaviour nobody can observe is a place where a test is asserting the wrong thing, or is asserting nothing.

**`ORDER BY position` without the tie-break passed every behavioural test in `internal/store`.** `ReplaceRuleModules` inserts in `determinism.Order` order and SQLite answers the `WHERE campaign_id = ?` lookup from the primary key index, so a table built through this package's own write path comes back in module-id order whichever `ORDER BY` it is given. Rows inserted by hand in reverse id order came back in id order too. The difference only appears for rows written by something else, and only under a different plan — which is why the order is now also asserted where it is written, by reading the keys out of the statement and using them.

**Moving the validation inside the write transaction changed nothing observable,** because the writer wraps the error with `ErrWriteFailed` and the transaction rolls back. The claim "a rejected write leaves the previous set intact" is true either way. What the pre-validation ordering actually decides is which of two simultaneous mistakes a caller is told about, and `TestAMistypedModuleIdIsReportedInPreferenceToAnUnknownCampaign` holds that specifically rather than implying the ordering is load-bearing when it is not.

A real violation in rule code was injected in both directions, and both layers fired: `time.Now` in `rules.Context.Rand` produced a `forbidigo` finding *and* two audit findings (the import and the call); a map range produced no lint finding and one audit finding. The same probe in `internal/domain/systems` — a directory that did not exist when this work started, and which `RuleDirs` named anyway — produced the same two findings from both layers with no edit to any configuration, which is the claim about the forward-looking scope demonstrated rather than asserted. The audit's own meta-test — one fixture per table entry, each required to be objected to by name, plus a closure asserting every entry has a fixture — is what makes "the audit works" a claim rather than a hope, and its sanctioned-forms test is the one that decides whether the rules are rules or noise.

`internal/domain/rules/rules_test.go` still holds its own import audit, `TestNoRuleFileImportsAClockOrAnAmbientSourceOfRandomness`. It is left in place: that file is not this work item's to edit, and it checks one thing this package's audit deliberately does not — that `math/rand/v2` *is* imported, which is how the one permitted `rand` package stays required rather than merely un-forbidden. It is a narrower sibling over one directory, not a second answer to a different question.

## Alternatives considered

**Write the `forbidigo` patterns in `.golangci.yml` and the selectors in Go, with a test comparing them by hand.** Rejected: that is three lists, not two, and the test would itself need updating when a rule changes — so the rule now has three places to be edited and one of them is a test. Deriving the configuration makes the list impossible to get wrong rather than merely checked.

**Generate `.golangci.yml` from the table.** Rejected: the linter's configuration is the phase integrator's file, and a generated one would put a build step between `golangci-lint config verify` and a file a human reads during an incident. The derivation goes the other way, from the file to the table, and the direction of the dependency is the point.

**`depguard` instead of `forbidigo`, forbidding the imports rather than the calls.** Rejected, and not because it is wrong: forbidding `time` outright is stricter and would cover a `time.Duration` a rule resolver used for no reason. But S-10.4's rules are about what a resolution can *depend on*, and a package that is imported and never called is already caught by the audit's import rule — while `depguard` cannot express map iteration at all. Two linters for one table would be two configurations to keep in step, which is the problem this record exists to solve.

**A type-aware audit with no linter at all.** Rejected: it is the stronger of the two mechanisms and it is the one that runs only when somebody runs `go test`. `AGENTS.md` puts it exactly: a gate that can be skipped by not running a command is a gate nobody runs, and `golangci-lint run` is in `make check` for every contributor whether or not they read this file.

**A syntactic audit — detect a map range by looking for a map literal or a call to `maps.Keys` — with no type checking.** Rejected: it cannot see a map behind a struct field or a function result, so `for k := range s.weights` and `for k := range buildWeights()` would both pass, which is the shape of an audit that cannot fail. Type information is what makes the rule the rule, and it costs about a second.

**Forbid map iteration with `//nolint` on the sorted form.** Rejected: `nolint` is per-line and `forbidigo` matches the `maps.Keys` call wherever it appears, so every sanctioned use would need a suppression comment, and a rule whose correct uses all carry a suppression is a rule the next contributor deletes rather than reads around.

**A `Scope` that takes the registry, so `Admissible` can look up what a module id means.** Rejected: it would make `domain` depend on the plugin registry, and `internal/domain` imports nothing from the project by rule. The check is a pure function over a compiled-in value, which is what lets `houserules` call it at registration without either package importing the other.

**Store `Scope` in the `config` column, so the store can refuse an inadmissible module on write.** Rejected twice. It would put a vocabulary this record does not own into a JSON document `houserules` owns, and it would be the wrong layer: the store cannot know which modules this build has, so it cannot check anything a registry would not check better, and a check the store performs for a registry that does not exist is a second answer waiting to diverge.
