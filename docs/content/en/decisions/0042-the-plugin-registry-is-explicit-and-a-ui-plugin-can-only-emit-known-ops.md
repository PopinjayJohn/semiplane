## Context

[0011]({{ "decisions/0011-compiled-in-plugins/" | relURL }}) decided that plugins are compiled in and registered in the composition root, and [0012]({{ "decisions/0012-plugin-authority/" | relURL }}) decided that plugin authority is enforced structurally: a gameplay plugin resolves intents into mutations, a UI plugin may only emit operations a gameplay system already resolves, and neither can write state because resolution *returns* what should change. [0041]({{ "decisions/0041-the-rules-contract-returns-mutations-and-carries-its-own-rng/" | relURL }}) built the contract the two tiers are typed against.

What is left is the machinery those three records assume exists, and each of its three parts had a genuine question in it.

**The vocabulary is the system's answer, and nothing can ask it.** `rules.System` has nine methods and none of them declares which operations the system resolves. That is deliberate on [0041]({{ "decisions/0041-the-rules-contract-returns-mutations-and-carries-its-own-rng/" | relURL }})'s reasoning — a tenth method makes every future method a breaking change for every plugin — and `realtime` draws the same line when it validates an op's *shape* and leaves membership to the system. But §10.3's rule is a question about the build: *"a UI plugin may only emit operations **some gameplay system already resolves**"*. Asking it requires the system's answer, and the answer was somewhere nobody could reach.

**A system's mutations are opaque, and somebody has to apply them.** `rules.Mutation.Args` is the system's own payload, which semiplane transports and never interprets (S-12.3), and `realtime.Placement` is semiplane's envelope of position, hit points, conditions and visibility. Nothing in either package's vocabulary says what the first means for the second. Only the system can: it is the code that wrote the encoding in `Object.Data`, so it is the only code that can read it back out of `Mutation.Args`. Without a named place for that, either the adapter interprets payloads — which is exactly what S-12.3 forbids — or every system reimplements the same projection and the second one disagrees with the first.

**The recovery boundary is wider than `Apply`.** §10.8's row is *"gameplay plugin panics inside `Apply` → `recover()` at the `Apply` boundary; return an error; state is not mutated because mutations are returned, never applied in place"*. Two of those three claims are about the signature and hold by themselves. The third — that state is not mutated — needs the *order* of the surrounding code to be right, and it turns out that a codec is plugin code too: it runs once building the snapshot a system resolves against and once per mutation decoding a payload. A `recover` around `System.Apply` alone contains a system and not a codec, and the first version of this code did exactly that. `TestAPanicInsideACodecLeavesTheStateByteIdentical` found it, which is the argument for writing the test as a claim about the outcome rather than as a claim about the function.

## Decision

**Two registries, one per tier, and no `init()` in either.** `internal/plugin` holds the gameplay systems; `internal/web/plugins` holds the UI plugins, and the second is built *over* the first because the one question it asks is a question about the build. Both list in registration order and both return a fresh slice per call: with versioned packs the order is reviewable information (ADR 0011), and a shared slice is mutable global state in a package whose whole argument is that there is none. `internal/plugin` holds a test that parses the source of every package in the tier for `init`, because a rule that is easy to lose in a refactor is worth a test rather than a comment.

**Registration asks `rules` and adds nothing.** `Register` calls `rules.Validate`, uses `rules.Kind.Valid` for a UI page type's kind, and refuses only what nothing upstream has an answer for: a duplicate id, a missing codec, and a name claimed twice within a tier. The test table pins the *upstream* sentinel for each case rather than "some error", so a registry that reimplemented `rules`' checks would fail it. The same rule governs the wire: this package does not keep a second copy of the eight `RejectReason` words, because `realtime` verifies what it is given and degrades anything outside the set to `server_error` — the safe direction.

**An unknown system is a type carrying the id.** `Registry.Resolve` returns `*UnknownSystemError`, which satisfies `ErrUnknownSystem` and names the id it wanted, because S-10.6 and §10.8's first row require the refusal to *say which ID it wanted* and a bare sentinel makes that a property of the caller. It does not satisfy `ErrMalformedPlugin`, deliberately: a missing plugin and a malformed registration are different events with different owners.

**A kind is registry-backed, an unknown kind is inert, and two systems may declare the same one.** §10.7 makes `kind` a property of the running build, so semiplane's five register as built-ins and a system's `ContentKinds()` join them. What is *not* enforced is validation against that set, because §10.8's last row makes a stale kind degrade to prose with its content intact and S-3.3 makes a page whose kind nothing registers inert; `KnownKind` exists for presentations that want to be specific, and every caller that asks it must have the prose answer. And a kind two systems declare is **recorded twice, not refused**: §10.2.1 asks for that in as many words — a system registers its own `ancestry` "without colliding with, or being blocked by, 5e's vocabulary" — and both 5e revisions declare `spell`, so refusing the second declaration would make 5e-2014 unregistrable in any build that has 5e-2024.

**The operation vocabulary is asked through a second, optional interface.** `plugin.Operations` is one method, `Resolves(rules.Op) bool`, and it is not on `rules.System` because [0041]({{ "decisions/0041-the-rules-contract-returns-mutations-and-carries-its-own-rng/" | relURL }}) argued against exactly that. A system that does not implement it contributes no operations, so a UI plugin that declares one is refused at registration — the safe direction, because the alternative is asking nobody and assuming yes, which is how a plugin ships a button whose operation the game refuses at the table with the plugin's name on it. It is `realtime.validOpShape`'s separation again: shape is checkable anywhere, membership is the system's answer.

**`Codec` is the one thing a system must supply, and `PlacementCodec` is the one with no opinion in it.** An object is its placement, encoded as that placement's own JSON, and a payload is written back onto a draft. The two halves are one interface and not two seams because the only code that can read a system's payload is the code that wrote its `Data`, and two seams would be two places to disagree. The draft matters as much as the codec: a decode failure has to arrive *before* the hub stamps a version, or the placement advances a version while nothing about it changed and a client reconciling against it waits forever for a delta that never comes.

**"An error means nothing was applied" is enforced by the shape of one function.** `settle` is the only function that calls `System.Apply`. It holds the result in a local, every error return is `return nil, err`, and it returns `([]realtime.Change, error)` — so there is no value anywhere in this package holding mutations and an error at once, and a system returning `([]Mutation{…}, err)` has them dropped by the code rather than by a check. A check of the form `if err != nil && len(mutations) > 0` is a thing a later edit can delete.

**The recovery boundary is `settle`, not `Apply`, and the reason is ordering.** Snapshot, resolve and decode all run plugin code; only `commit` writes, and it calls `internal/realtime` and nothing else. So one `recover` around the whole resolution contains a panicking system *and* a panicking codec, and when it fires nothing has been written — which is what "state is not mutated" means, as a consequence of the order rather than a review promise. The residual is stated rather than hidden: a panic inside `CampaignState.Mutate` itself would also be recovered after the first write, and that is semiplane's own code.

**The panic value is dropped and its type is kept.** A panic value is routinely the payload the resolver choked on, which on this project is a dice result or a `[!secret]` callout body, and S-12.3 forbids an event carrying either. `PanicError` records `%T` and nothing else, so `plugin.panicked` is an alertable class and a log line cannot leak what a plugin choked on.

**The seed is per resolution, not per campaign.** `rules.Context.Rand` derives a source from `(seed, label)`, so one seed per campaign would make every `roll` in that campaign draw the same number — a roll log that is one value repeated, which is the opposite of §16.3's audit. The adapter mints a fresh seed per resolution from `crypto/rand.Reader` and hands it to the system; reproducibility rests on the system putting it in its mutation payload, which is where §16.3's per-session seed belongs. `crypto/rand` here is not the source S-10.4 forbids: the hub is where entropy enters a process and `rules.Seed` is where it becomes a recorded value.

**The refusal vocabulary is the system's, in a type with two fields.** `plugin.Rejection` carries a `RejectReason` and the system's own error, and `Error()` prints only the reason. `rules.System.Apply` returns a bare `error` and `realtime.RejectionError` is a hub-side type this package must not construct on a system's behalf, so without a bridge every refusal would arrive as `server_error` — safe and useless, because a GM whose `set_hp` was refused as `not_your_turn` and one whose refused `set_hp` hit a bug would be told the same word. The separation is S-12.3 again: the reason reaches a browser, the detail is reachable through `errors.Is` and printed by nothing.

**A UI plugin is handed a `Reader` and an `Emitter`, and those two types are the whole of its authority.** `Reader` has three methods — the campaign, the role, and one render query — and **no method that writes and no reference to the hub's state**, which is §10.2's "writes `campaign_state`: UI never" as a property of a type rather than an instruction. Its read access is filtered by the reader's campaign visibility *before* the value reaches the tier, by the same construction ADR 0024 uses for authorisation: a gate mounted, not a check inside a handler. `Emitter` takes a `domain.Requestor` and a `rules.Intent` and nothing in which to name a campaign or a role, so the actor is the account that loaded the page and a plugin cannot escalate by being clever; it dispatches the same intent a keystroke would, so the access gate, the codec's bounds and the system's own role check all apply to it identically (§10.3's "identical authorisation and validation").

**A UI plugin's declared operations are checked at registration, and nothing else about it is checked against another package.** `Declaration.Emits` is the only field whose authority is a question about the build. The check asks whether *any* registered system resolves the op, not whether the campaign being rendered does: an op is emittable if some system resolves it, and a plugin that emits `roll` on a campaign whose system does not gets `unknown_op` from the adapter like anyone else.

## Consequences

**Three seams the composition root must supply, and two of them are one-liners in a package this work item does not own.** The wiring is:

```go
systems := plugin.New()                                  // built-ins only, no plugins yet
_ = systems.Register(plugin.Entry{System: dnd5e.New2024(), Codec: dnd5e.Codec{}})
resolver, err := plugin.NewResolver(plugin.ResolverConfig{
    Systems:  systems,
    States:   states,                                    // the hub's realtime.Registry
    SystemOf: campaignSystemID,                          // reads campaigns.system_id
})
hub := realtime.NewHub(ctx, realtime.HubConfig{States: states, Resolve: resolver})
ui := webplugins.New(systems)
```

`SystemOf` is a closure over the store, because `internal/store` is not this package's to read. The `Emitter` implementation is the one real gap: `realtime.Hub.Apply` resolves a `*ClientIntent` against a `*Peer`, and `Peer` is admitted by `Join` — a real connection with a presence entry and a slot in the campaign's peer limit — so a UI plugin has no path to it. `internal/realtime` needs a method that resolves an intent on behalf of a viewer and broadcasts the result; that is the integrator's to add, and it is the only change outside these three paths this work item needed.

**A page type registered here is unreachable until somebody mounts it.** `PageType` holds the declaration and `internal/httpapi/router.go` holds the mount, so this package claims no route and appears in no accessibility audit. A render hook is the same shape: `internal/content` owns the Markdown pipeline and this package does not import it, so a registered hook is inert until the pipeline's owner asks this registry what it holds, and `RenderHook.Kind` is the kind of page rather than a Markdown node because the pipeline has no node vocabulary semiplane owns yet. Both are stated on their types rather than left to be discovered.

**The adapter holds no authorisation list and no operation table, deliberately.** §7.2's GM-only rule lives in the system, which branches on `call.Role` and returns `not_permitted`; a list here would be a second answer to a question `realtime.Core` already had to fake, in a function whose own comment calls the fake a shape test rather than an authority. Ordering is preserved by construction: the adapter checks the envelope, the system checks the role.

**Two contract gaps are reported rather than closed.** `CampaignState.SetPaused` is unreachable through this adapter: `rules.Mutation` has no campaign-level half, and its own comment says a pause is an intent whose resolution is *no mutations* — so a pause resolves to nothing observable, which is a gap in the contract rather than in the registry. And `realtime.Placement` has no per-object field for a system's own state, so a system's `Object.Data` is derived from the five envelope fields; a system with per-object state of its own needs the `realtime` side to carry it. Neither is something this work item could fix without editing `internal/realtime`.

**Three invariant tests were checked by mutation, and one of them found a bug.** Deleting the `recover` from `settle` reproduces the panic escaping and fails `TestAPanicInsideApplyLeavesTheHubStateByteIdentical`; ignoring the error from `System.Apply` fails `TestMutationsReturnedWithAnErrorApplyNothing`; dropping the currency precheck fails `TestAVersionThatMovedUnderAResolutionIsRefusedWhole` with `p1` partly moved. The duplicate-mutation check is the fourth: it passed before the reason column was pinned, because it and the currency check shared one map and the second mutation naming a placement read the first one's slot as a version of 0 and was refused as `stale_version` — the right outcome blaming the client for the plugin's mistake. Pinning the reason per case is what turned that into a bug report rather than a green check.

## Alternatives considered

**Put the operation vocabulary on `rules.System` as a tenth method.** Rejected, and [0041]({{ "decisions/0041-the-rules-contract-returns-mutations-and-carries-its-own-rng/" | relURL }}) already argues why: every future method becomes a breaking change for every plugin. A second optional interface costs one small method on the systems that want to be emittable from, and leaves the rest alone.

**Ask the UI tier to trust the plugin's declaration, or to check at emit time.** Rejected: a trust-based check fails at the table with the plugin's name on the refusal, and a runtime check means the first thing that learns a plugin emits `set_hp` is the campaign that tried.

**Let the adapter interpret `Mutation.Args`.** Rejected: S-12.3 and `rules.Intent.Args`'s own comment both say semiplane transports an opaque payload and never interprets it, and a JSON-shaped guess at a system's private schema is a second answer that only holds until the system's second pack.

**Recover around `System.Apply` alone, as §10.8's row reads.** Rejected by the codec-panic test. The record's row is right about the *intent* — a panic mutates nothing — and the boundary is wider than the call it names because a codec is plugin code that runs on both sides of it.

**Make the currency precheck unnecessary by holding the hub's lock across a resolution.** Rejected: it would serialise every campaign in the process behind whichever one is resolving, and ADR 0004's whole subject is what this process may and may not share. The precheck buys refusing a stale list *whole* rather than not existing.

**One registry for both tiers, as ADR 0011's sketch shows.** Rejected: §10.2's table gives each tier its own registration package, `rules.View.RendererPlugin` says a component lives in the UI tier under the view's name, and `internal/domain/rules` must not import templ — which it would have to reach a component from a shared registry's map. Two registries, with the UI one holding the gameplay one, keeps the dependency one-way and the reasoning separate.
